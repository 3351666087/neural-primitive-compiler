## 2. 为什么不需要 GPU

- 主要耗时是 Python 循环中的逐时间步递推与网格搜索，每一步只有 3.2 万个元素；GPU 的启动、数据传输与编译开销会超过计算本身。
- 没有任何一步受内存限制（峰值内存 < 1 GB）。
- 唯一可能需要 GPU 的工作是用规则生成的或置乱的连接组重新训练 flyvis（每个模型数个 GPU 小时 [估]），它不在预注册的设计中（`PRE_REGISTRATION.md` §4 用实测输入响应，不训练），为使用 GPU 而加入它违反任务书 §0 第 8 条。

## 3. 若推翻条件出现：标定会话方案

只有当 `GPU_RESOURCE_DECISION.md` 的推翻条件成立（例如候选需要参数量 > 10⁶ 的可训练模型，或某个必要基线在 CPU 上超出资源上限）时，才按以下顺序考虑，并先按 §10A.3 的完整模板发出申请、等待用户回复"GPU已开机"：

1. **先在 CPU 上测小样本**：固定种子、同一份输入，测每批耗时、峰值内存、I/O，写入本文件。
2. **便宜卡优先**：先申请 24 / 32 GB 档的短时标定会话（30–60 分钟，由实际吞吐决定），测：(a) 驱动 / CUDA / PyTorch 版本与内核兼容性；(b) 同一批的吞吐与显存；(c) 编译开销；(d) 断点保存与恢复；(e) 结果传回本地的时间。
3. **退出阈值**：GPU 吞吐不到 CPU 的 5 倍，或每元有效样本不优于 CPU，或兼容性在 15 分钟内无法解决：停止新任务，保存日志，立即发出【需要你关闭GPU】请求。
4. **96 GB 卡只在有证据时考虑**：便宜卡显存不足且模型无法分块时。没有这一证据时拒绝升级（`tests/test_gpu_protocol.py` 场景 7）。
5. **时间盒与兜底**：开机前与用户约定无人值守上限，或由用户配置自动停机；没有可靠的兜底时只做有人监督的短会话。
