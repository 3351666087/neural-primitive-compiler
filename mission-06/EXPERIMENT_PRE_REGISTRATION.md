### G0.2　适用性的独立证明器 APP-R（设计锁定）

**适用性**指：在每个合格状态中，选择规则都给出 (d, s)，且搬运能执行。合格状态 = 原子被违反 ∧ 原子单独可满足 ∧ 存在非危险空格。

搬运在合格状态中总能执行：若 d 被占，则存在一个非危险空格 e，且 e ≠ d、e ≠ s。所以适用性等价于两点：目的候选集足够大，并且在所选的 d 下来源候选集足够大。

APP-R 是计数抽象的**松弛**：它只加入每个具体反例都满足的必要条件。因此 UNSAT 即证明。

- **位置类。** 线被 d 分成三部分：左、d 本身、右。再按以下区间的归属细分：
  - 原子的区（ZONE 原子）；
  - 窗口 W1、W2（区间 [s_v, s_v + c)，c = A1 个数，可能不存在）；
  - "距 d 不超过 k"。

  每类的大小由区间交集的容斥给出，N 为符号整数。
- **类型计数。** 每类有六种类型的计数：
  - E：非危险空格；H：危险空格；
  - O：A1；P：A2（仅 ORDER）；
  - X：其他可拾取物体；F：NO_PICK 物体（非原子颜色）。

  各类型计数之和等于类的大小。
- **见证位置。** 以下位置都带类型，并按位置归入相应的类：
  - 违反见证。ORDER：i < j，类型 P、O。ZONE：区外一个 O。GROUP：i < k < j，类型 O、非 O、O。
  - 空余格 e（类型 E）。
  - 目的格 d。

  见证所在类的相应计数 ≥ 1；GROUP 的两个 O 见证在同一类时，计数 ≥ 2。
- **可满足性**（单原子，精确条件）：
  - ORDER 总可满足；
  - ZONE：区内允许格数（总数 − H − F）≥ A1 个数；
  - GROUP：W1 存在。
- **窗口的必要条件：**
  - 存在的窗口内 H = F = 0；
  - 两个都存在时 s_1 ≤ s_2；
  - 窗口不存在时，H + F ≥ ⌊N / c⌋；
  - "最左（最右）"的极小性被放弃（松弛）。
- **选择：**
  - 目的候选 = 目的区域内、类型属于目的类型的格子；
  - pick 最左：左侧部分的候选数为 0；pick 第二最左：左侧部分的候选数为 1；最右与第二最右对称；
  - 来源候选 = 来源区域内的 O（区域可以依赖 d）。
- **两个查询：**
  - Q1：合格 ∧ 目的候选数 < 需要数（第二种 pick 需要 2 个，其余需要 1 个）；
  - Q2：合格 ∧ d 是被选中的目的 ∧ 来源候选数 < 需要数。

  两者都 UNSAT 时为 PROVED；任一为 SAT 时为 NOT_PROVED，并附模型；超时为 UNKNOWN。
- **范围：**
  - S_T（真值分布推广到一切 N）：H ≤ 2，K ≤ N − 1。
  - S_D（部署分布）：S_T 再加 K ≤ 7。
  - S_A：H 不限。

  三者都有 N ≥ 3。

  NO_PICK 作用于原子颜色时，达成器按定义不适用；构造器的 `_gate` 已单独拒绝这种情形，不属于本证明的范围。

**具体化。** 对 NOT_PROVED 的模型，按类计数与见证给每个格子分配类型，再赋予颜色：
- O → 1，P → 2；
- X → 3（非 ORDER 时可为 2 或 3）；
- F → 4，并令 fixed = (4,)；
- H → 危险空格。

类内顺序随机重排，最多 500 次。然后用构造器侧的 `dsl.select_dsl` 与 `libval2.eligible` 逐个判定，得到的才算具体反例。每个反例记录 N、H、K 与所属范围。

**新代码的隔离：** G0 的新代码中，构造器侧模块不得导入 `truth`、`judge/*` 或任何真值表。真值只在评分脚本中读取。这一点由静态检查（G0.T）强制。

### 修正 G0-1（开发期间，正式运行之前；预测与阈值不变）

开发只在新生成的随机规格上进行（`rand_specs.sample`，种子 606、607，共 1,520 个实例，与 AUD 不重叠）。唯一的例外见第 2 条。

1. **APP-R 的窗口约束加强**（全部是必要条件，所以松弛仍然可靠）。开发集上的虚假模型都来自窗口：松弛允许窗口放在任意位置，或允许窗口"不存在"，而真实的最左（最右）可行区段在别处。新增约束：
   - 极端端点外侧的边界条件：W1 左侧的格子、W2 右侧的格子（若存在）是阻挡格（H 或 F）。
   - 两条侧区间作为新的基本区间：BW1 = [0, s_1)，BW2 = [s_2 + c, N)。侧区间中，除紧邻窗口的那格外，每 c 格至少一个阻挡格：阻挡数 ≥ 1 + ⌊(长度 − 1)/c⌋。侧区间内每个区间 J（某部分与若干基本区间的交）的阻挡数 ≥ ⌊|J|/c⌋。
   - 窗口不存在时，每个区间 J 的阻挡数 ≥ ⌊|J|/c⌋。另外，每个非阻挡类型的见证格位于长度 < c 的区段内：两侧有阻挡格或线端，且两者距离 ≤ c。
   - 存在的窗口之外、位于侧区间的非阻挡见证格，同样位于长度 < c 的区段内。

   开发结果（最终版本）：
   - 种子 607 的 1,402 个实例中，"APP-R 证明而 N ≤ 5 真值有反例"的情形为 0 个。
   - 其中 20 个在 N ≤ 5 上适用：12 个被证明。其余 8 个由 APP-R 的无界模型具体化出真实反例，N = 13..634。这 8 个在 N ≤ 7 的真值里都有反例，首次出现在 N = 6 或 7。
   - 中间版本在种子 606 上的界内测试（N ≤ 5）中，7 个适用实例全部被证明，没有错误证明。
2. **G0-A5 不再是盲测。** 开发的第一次冒烟测试是在 12 个 LIB 实例上运行的，结果为 12/12 PROVED。这发生在本修正之前、代码提交之前。G0-A5 照常评分，但标注为"非盲"。
3. **编译器的程序类。** 开发中发现：寄存器从自身或程序中更靠后的寄存器装载时，`compile_cir` 会抛出异常。原因是 `cog.prims.cmr` 把尚未建立的 Y 神经元当作输入通道，之后再建立同名神经元时报重复。这是响亮的拒绝，不是错误编译。据此明确：
   - 类 C = CIR 解释器接受的程序（G0-K2 的生成器）；
   - 类 C_K = C 中，寄存器只从更早的寄存器装载的程序。定理（T-K）的范围是 C_K。
   - G0-K2 的判定：C_K 内的不一致数（两个模拟器）= 0，C_K 内的编译异常 = 0，C \ C_K 的程序全部被响亮拒绝（`outside_C_K_compiled` = 0）。任一不满足即不成立。
4. **G0-M1 的两种安全变体。** 裁判的实例只使用目标颜色、安全颜色与干扰色 4。单原子目标若加 NO_PICK 4，就没有"其他可拾取物体"。所以每个实例跑两种变体：
   - fixed：NO_DROP_HAZARD 加 NO_PICK 4；
   - movable：只有 NO_DROP_HAZARD，颜色 4 是可拾取的干扰物。

   判定不变：总不一致数 = 0。开发时的负对照（把空余格改为最右）在 3 组中各检出 100 至 700 处不一致，说明比较不是空的。
5. **开发中的观察**（不是 AUD 的结果）：含"距 d 不超过 3"的规格，有几个的第一个反例恰好出现在 N = 7。也就是说，对 k = 3，N ≤ 7 的穷举没有余量。

### G1-A.2　P-ALF-1：适用性的可观察性（预测锁定）

**设计修订（提交之前，没有任何数据）。** 第一稿只测原始命令的适用性。但在 ALFWorld 中，到达或打开一个容器就会显示它的局部状态。所以原始命令的适用性几乎总能由观察判定，第一稿的"U ≥ 0.5"会因为一个平凡的原因不成立。Mission 05 的合同类型针对的是**达成器（宏技能）**的适用性，所以现在两个层次都测。

**问题。** Mission 05 的合同类型把适用性当作"当前状态上可判定的谓词"。在 ALFWorld 中，只用构造器的合法观察历史：
- (P) 原始命令的适用性有多少可判定？
- (M) 与目标相关的宏技能"取得一个 X"（X 为目标中的物体类型）的前置条件"知道某个 X 在哪里"，有多少可判定？

**设计：**
- 游戏：训练集中按种子 61 抽 60 个（每类任务 10 个）。
- 驱动：裁判侧的随机合法策略。每步从 `admissible_commands` 中均匀抽一个，排除 `look`、`inventory`、`examine`、`help`。每局 20 步。这只是测量装置，不是构造器。
- 裁判侧记录：每步的文本观察与合法命令集合。
- **P 层：**
  - 查询集合：一局中曾经合法过的全部技能命令，动词为 go to、open、close、take、move、heat、cool、clean、use。
  - 构造器侧判定器 `belief_applicable(history, command)` 只读到该步为止的文本观察，输出"适用 / 不适用 / 未知"；规则来自 ALFWorld 文档中的动作语义（设计者知识）。
  - 真值：该步的合法命令集合。
- **M 层：**
  - 构造器侧解析第一条观察中的目标文本（"Your task is to: …"），得到目标物体类型 X。解析器使用 ALFWorld 的目标句式，是设计者知识。
  - 每一步，构造器的信念中是否已有某个 X 实例的位置（只来自观察）。
  - 裁判侧核对：该位置是否正确，即信念中的位置是否真有该物体（用后续的合法命令或环境事实）。

**度量：**
- U_P、W_P：P 层中判为"未知"的比例，以及确定判断与真值不符的比例；
- U_M：M 层中"不知道任何 X 在哪里"的步的比例；
- W_M：M 层中信念位置错误的步的比例；
- S0：第 0 步就知道某个 X 位置的游戏比例。

**预测：**

| 编号 | 预测 | 依据 |
|---|---|---|
| ALF1-a | U_P ≤ 0.05 | 到达与打开会显示局部状态；不在场的命令确定不适用；go to 只依赖已列出的容器 |
| ALF1-b | W_P ≤ 0.02 | 残余误差来自文本解析与对动作语义的理解 |
| ALF1-c | U_M ≥ 0.5 | 物体位置在看到之前未知；20 步随机探索只访问少数容器 |
| ALF1-d | S0 ≤ 0.1 | 第一条观察只列出容器，不列出物体 |
| ALF1-e | W_M = 0 | 只有代理自己移动物体，看到的位置不会失效 |

**解释（事先写定）：**
- a、b、c、d 都成立：在原始动作层，Mission 05 的合同类型（可判定的适用性谓词）加上观察适配器可以迁移；在达成器层则不行。"取得 X"的适用性取决于未观察的状态，只能借助：
  - (i) 环境契约中的存在公理（每局可解，故目标物体存在），记为信任；
  - (ii) 定义在信念上的进度度量（例如尚未访问的容器数）。

  这是 Gate 2 的一个最小失败机制，并直接给出 Gate 3 的候选方向：带信念的适用性。
- a 或 b 不成立：观察适配器本身不可靠，失败更早发生。
- c 不成立：部分可观察性在这一设置中比估计的弱。

**预算：** 60 局 × 20 步，CPU < 30 分钟。

## §G1-B2P0　B2 用本会话的子 agent 的可行性试点（锁定于运行之前）

**用户的补充（2026-10-21）：** 供应商 Anthropic，模型 Opus 5.5；优先使用本会话的子 agent 作为 B2，先看是否可行。

**这一路线的含义：**
- 不需要 API 密钥，花费按子 agent 报告的 token 数记账，算在用户的 Claude Code 额度内。
- B2 与设计者（本会话）是同一模型。这对"强 LLM 代理"基线是允许的。但它带来两个风险：
  - (i) B2 的轨迹回流到设计者，成为构造器的知识来源；
  - (ii) 子 agent 有文件系统访问权，可能读到裁判侧数据，例如 ALFWorld 的专家计划。

**试点（只在 ALFWorld 训练集上；不接触 WorkArena）：**
- **游戏**：训练集中按种子 62 抽 2 个，来自不同任务类型，并排除 P-ALF-1 用过的 60 个。
- **裁判侧服务器** `experiments/b2/alf_server.py`：持有环境，经本地 Unix 套接字只返回文本观察。不返回合法命令列表、`won` 或分数。每局最多 40 步；代理发出 `done` 或用满步数即换下一局。服务器把命令、观察与真实成败写入只属于裁判的日志 `experiments/b2/run/judge_log.jsonl`。
- **客户端** `experiments/b2/alf_client.py`：`reset`、`act "<命令>"`、`done` 三个动作，每次只打印一条观察。
- **子 agent 的指令**：
  - 只用客户端与环境交互，每次一个动作；
  - 不读取仓库或数据目录中的任何文件；
  - 结束时只报告局数、各局步数、自评是否完成、工具调用次数，不复述轨迹。
- **设计者的隔离**：本会话不阅读子 agent 的轨迹与裁判日志中的观察文本，只用脚本从日志中计算聚合量：成败、步数，以及命令中是否出现读文件的迹象。
- **花费**：步数上限是唯一的硬上限（2 局 × 40 步）。子 agent 报告的 token 数记入 `experiments/b2/cost_ledger.jsonl`。

**预测：**

| 编号 | 预测 |
|---|---|
| B2P0-a | 子 agent 能按协议完成两局：服务器日志中两局都有 reset，且每局至少有一个动作 |
| B2P0-b | 服务器日志中没有越界：所有命令都来自客户端；子 agent 的报告中没有轨迹复述 |
| B2P0-c | 每步的平均 token 消耗 ≤ 30,000（以子 agent 的总 token 数除以总步数计）；若超过，则在 WorkArena 上（观察更长）不可行，需要换成 API 路线 |

成败率不做预测：2 局只用于可行性，不用于比较。

**协议偏差（如实记录）：** 本节的预注册，以及服务器、客户端与评分脚本，是在子 agent 开始运行之后才提交的。运行开始之后，这些文件没有任何改动（提交即是运行时的版本）。子 agent 的最终报告到达之前，本会话没有查看任何结果。

## §G2-0　Gate 2 的设计修正（运行之前；对 P-AW-0 的自我批评）

**问题。** `HYPOTHESES.md` 的 Gate 1 锁定版把 P-AW-0 定义为"冻结 Mission 05 的合同核心，只写透明适配器，记录每个任务首先卡在哪一层"。但 Mission 05 的目标语言是 LINE 专用的原子（ORDER / ZONE / GROUP 作用于一行格子）。按字面理解，AppWorld 的全部任务都会在第 1 层失败，这是由定义决定的，预测"≥ 30 % 卡在第 1 层"必然成立，几乎没有信息量。

**修正：把冻结的部分与需要适配的部分分开。**

1. **冻结的"合同核心"**（与领域无关，原样使用）：
   - 目标 = 状态谓词的合取；
   - 达成器 = 带合同的状态转移，合同含进度、两两保持与适用性，并带证据标签；
   - 优先级组合引理 L1；
   - 构造器 A-P（两两保持）与 A-P′（共享势函数）；
   - CIR 到 IF 网络的编译（T-K）。
2. **适配器**（领域专用，全部记入 `KNOWLEDGE_PROVENANCE.md`，计入知识成本）：
   - 谓词的求值器（从合法观察计算真假）；
   - 达成器的实现（宏）与合同；
   - 从自然语言目标到谓词合取的**统一**解析器（冻结一次，禁止逐题翻译）。
3. **P-AW-0 改为两部分：**
   - **(a) 任务结构剖面**（客观，裁判侧）：对开发集中按种子 64 抽的 40 个任务，从公开的开发集标准解法与测试中计算：
     - 是否需要提交答案值；
     - 涉及的应用数，读调用与写调用的个数；
     - 是否有循环或分页；
     - 写调用的参数是否依赖先前读调用的结果（关系绑定的深度）。

     这些量只描述任务需要什么，不作为构造器输入，标为"裁判侧任务结构测量"。
   - **(b) 冻结核心的覆盖**：按上面的剖面，逐项判定冻结核心本身是否缺少相应的结构。判定规则在运行前写定：
     - 需要答案值：核心的目标是状态谓词，缺少"信息目标"；
     - 关系绑定：核心只有开局时从观察绑定变量（Mission 05 的 cue），缺少运行中的查询绑定；
     - 循环或分页：核心的达成器是单宏，缺少对集合的迭代合同；
     - 写调用：核心只有不破坏两两原子的保持合同，缺少对全局"无附带破坏"的合同。

   **预测（锁定）：**
   - 需要答案值的任务占 ≥ 30 %；
   - 关系绑定深度 ≥ 1 的任务占 ≥ 60 %；
   - 有循环或分页的任务占 ≥ 30 %；
   - 至少两类缺口同时出现的任务占 ≥ 50 %。

4. **G2-ALF（真正的原样外推，ALFWorld 开发集）：**
   - 用冻结核心加记账的适配器，构造并运行 ALFWorld 控制器。适配器包括：原子 IN(o, r)、CLEAN / HOT / COOL(o)、HOLDING(o)、LIT(lamp)；达成器"取得 X""放入 r""清洗 / 加热 / 冷却""开灯"的宏，以及按 ALFWorld 文档写的合同。
   - 在开发游戏上记录：成功率；在哪一个合同上无法认证（预计：取得 X 的适用性，P-ALF-1）；以及失败时的实际原因。
   - 这一部分在下一节单独预注册，含成功率的预测与适配器的知识预算。
5. **最小失败机制（任务书要求至少 3 个，每个 ≥ 2 个竞争解释，再设计区分实验）。** 候选来自 G1 与上面两项：
   - (M1) 达成器层的适用性依赖未观察的状态（P-ALF-1）；
   - (M2) 未告知的环境结构破坏了观察适配器（同址关系）；
   - (M3) 信息目标与状态目标的错配（AppWorld 的答案型任务）；
   - (M4) 运行中的关系绑定与迭代；
   - (M5) 全局"无附带破坏"与两两保持合同的错配。

   M1–M5 的竞争解释与区分实验，在 (a)(b) 与 G2-ALF 的结果出来之后、Gate 3 之前登记。

**G2-0 / P-AW-0 结果（2026-10-21）：**

**锁定判定**（`experiments/aw/p_aw0.py`，40 个开发任务）：

| 预测 | 结果 | 判定 |
|---|---|---|
| 答案型任务 ≥ 30 % | 27.5 %（11/40） | **不成立** |
| 写调用的关系绑定深度 ≥ 1 的任务 ≥ 60 % | 72.5 % | 成立 |
| 有循环或分页的任务 ≥ 30 % | 95 % | 成立 |
| 至少两类缺口的任务 ≥ 50 % | 100 % | 成立 |

**协议偏差：** `p_aw0.py` 在运行之前没有单独提交，代码与结果一起提交。

**测量缺陷（POST-HOC 发现，`p_aw0_posthoc.py`，不改变判定）：**
- 每个任务最后都有一次 `POST supervisor/message`，即完成任务的协议调用。锁定版把它算作写调用，所以"有写调用"高估为 100 %。
- 所有解法都不出现 `page_index`（分页经由辅助函数），所以"分页"这一项无法用这一方法测量。

把 supervisor 的调用都当作协议之后：
- 状态改变型任务占 72.5 %，纯答案型占 27.5 %，**两者从不同时出现**；
- **全部状态改变型任务的写调用都依赖先前查询的结果**：深度 1 的 20 个，深度 2 的 7 个，深度 3 的 1 个，深度 13 的 1 个；
- 至少两类缺口的任务占 95 %。

**解释：**
- AppWorld 的开发任务分成两类。一类是信息目标（27.5 %），需要计算并回答一个值；另一类是带运行中关系绑定的状态目标（72.5 %），需要先查询、再按查询结果写入。
- 两类都需要迭代（95 %）。
- 冻结核心的目标语言（状态谓词合取，变量只在开局时绑定）无法表达其中任何一类。这为最小失败机制 M3（信息目标）与 M4（运行中绑定与迭代）提供了客观依据。

## §G2-ALF　冻结核心在 ALFWorld 上的原样外推（锁定于代码之前）

### 两个分支

- **G2A-0（严格冻结）：**
  - 构造器只接受带证据标签的合同，即 Mission 05 的规则：Z3 证明，或有界穷举。
  - ALFWorld 没有本项目的形式模型，所以没有任何合同能取得证据。
  - **预测：构造数 = 0**。这是一个由证据规则决定的结论，记录在案，作为"可证明适用性"层面失败的最直接形式。
- **G2A-1（公理化合同 + 运行时监控）：**
  - 合同改为**环境公理**，按 ALFWorld 文档的动作语义写出，标为 AX（信任，设计者知识）。
  - 运行时监控核对每一步的预期反馈；一旦违反，就记录违反类型并**弃权**（停止）。不做恢复，因为 Mission 05 没有恢复机制。
  - 组合用 Mission 05 的方法：优先级控制器，加上按两两保持选择原子顺序的 A-P。实现是对抽象合同表的重写，算法不变。

### 适配器（设计者知识，全部记账）

1. **统一的目标解析器**（冻结一次）：6 种目标句式 → 原子合取。
   - IN(T, R)、CLEAN / HOT / COOL(T)、HOLDING(T) ∧ LIT（台灯）、COUNT_IN(T, R) ≥ 2。
   - 句式中也包括 P-ALF-1 在训练局上发现的无冠词形式 "look at X under the desklamp"。
2. **观察适配器**：沿用 `belief.py` 的规则，即"一个容器一个位置"的先验，不加入同址关系（原样外推）。另加加热、冷却、清洗与开灯的反馈解析。
3. **达成器宏与公理化合同：**

   | 达成器 | 行为 | 公理化合同 |
   |---|---|---|
   | 取得(T) | 按初始观察列出容器的顺序逐个前往；关着就打开；看到 T 就拿起 | 适用性公理：T 存在（每局可解）；进度：未访问容器数（信念上的度量） |
   | 放入(T, R) | 前往第一个类型为 R 的容器；关着就打开；放入 | — |
   | 清洗 / 加热 / 冷却(T) | 带着 T 前往水槽 / 微波炉 / 冰箱，执行对应命令 | — |
   | 开灯 | 搜索台灯或落地灯，并使用 | — |

   两两保持的公理：放入保持 CLEAN、HOT、COOL；清洗、加热、冷却需要手持，会破坏 IN。所以 A-P 应把 CLEAN / HOT / COOL 排在 IN 之前。
4. **不使用任何先验的物品位置知识**：搜索顺序是初始观察中的列出顺序。

### 测试集与基线

- **游戏**：训练集中按种子 65 抽 60 个，每类任务 10 个，排除 P-ALF-1 与 B2P0 用过的游戏。每局最多 50 步。
- **B2（同一组游戏）**：子 agent，协议同 G1-B2P0，只报告聚合量。
- **B1（同库的经典方法）**：对 6 种目标句式各写一个固定的 HTN 方法，使用同一组宏与同一观察适配器，没有合同与监控。

### 预测（锁定）

| 编号 | 预测 |
|---|---|
| G2A-0 | 严格冻结时构造数 = 0 |
| G2A-a | G2A-1 能为全部解析成功的目标构造出计划（6 种句式都可表达） |
| G2A-b | G2A-1 的成功率 ∈ [0.30, 0.75]。本会话的估计：失败主要来自同址关系引起的监控违反，以及搜索耗尽步数 |
| G2A-c | G2A-1 的失败中，≥ 50 % 被监控检出并弃权，而不是沉默地失败 |
| G2A-d | B2 的成功率 ≥ G2A-1 的成功率（B2 有物品位置的预训练先验） |
| G2A-e | B1（HTN）与 G2A-1 的成功率差 ≤ 0.05：6 种固定句式下，合同组合与固定方法给出同样的顺序（H0-CLASSIC 在此成立）。G2A-1 的差别只在监控带来的弃权（安全失败） |

**预算：** 本机 CPU < 1 h；B2 合计 ≤ 3,000,000 tokens。

**G2-ALF 结果（2026-10-21；60 个训练局，每局 ≤ 50 步；`experiments/g2/g2alf_scores.json`）：**

| 预测 | 判定 |
|---|---|
| G2A-0 严格冻结构造数 = 0 | 成立 |
| G2A-a 全部可解析目标都能构造 | 成立 |
| G2A-b 成功率 ∈ [0.30, 0.75] | 成立（0.667） |
| G2A-c 失败中 ≥ 50 % 被检出 | 成立（20/20） |
| G2A-e \|B1 − G2A-1\| ≤ 0.05 | **不成立**（B1 高 0.20） |

**解释（反例）：**
- G2A-1 的 18 次监控违反全部发生在 `go to r`：没有出现"You arrive at r"。原因是 P-ALF-1 发现的同址关系：代理已经在 r 所在的位置。
- B1 不检查，照常继续，随后的打开、拿取都成功。
- 带监控的公理合同把一条**错误的设计者公理**（一个容器一个位置）变成了失败。这里"证书 + 监控"不但没有带来更高的可靠性，反而付出了 20 个百分点的成功率；B1 在这些局上并没有更多的沉默失败。
- 这是对"组合合同提升可靠性"（H-COMP）的一个最小反例：可靠性取决于公理是否正确，而公理来自设计者的先验。

**B2 的修正（运行之前）：**
- 子 agent 在一个对话中连续玩多局，上下文累积，token 消耗随步数超线性增长。按试点的单步约 4,100 tokens 估算，60 局会远超 3,000,000 的预算。

- G2A-d 在同一子集上比较 B2 与 G2A-1（以及 B1）。

|---|---|---|---|

### Gate 3 的选择

**选择 M2（与 M0 合并）。** 理由：
1. 它是本 mission 唯一一个直接**反驳** H-COMP 的结果：证书与监控降低了成功率。
2. 它与 F2（不借裁判的认证）直接相关。问题是，可靠性来自哪里：设计者公理，还是从环境中发现的规律？
3. 它的两个竞争解释可以用低成本、可证伪的实验区分，而且同一结构可以迁移到 AppWorld（M5 的框架公理，用于检验 H-XFER）。
4. M3、M4 的答案很可能是"属于程序综合"（H0-CLASSIC），信息量较小。M1 的位置先验是 B2 的优势来源，作为 Gate 3 的第二项（消融）一并测量。

## §G3-M2　Gate 3：发现被隐藏的环境结构，能否修复证书与监控的失败？（锁定于代码之前）

### A 阶段：B 的主动发现（开发局）

- **数据**：训练集中按种子 67 抽 20 个新局，与此前用过的局都不重叠。合计不超过 600 步。
- **触发**：每当 `go to r` 没有得到"You arrive at r"时，B 立即做区分实验：
  1. 先发出 `examine r`。它需要代理就在 r 的位置，且没有副作用。
  2. 再重试一次 `go to r`。
- **竞争假说**（由设计者写定，属于文法内的发现）：

  | 假说 | 内容 | 预测：examine r | 预测：重试 go to r |
  |---|---|---|---|
  | H_co | 同址：代理已在 r 的位置 | 成功 | 同样无效 |
  | H_un | 不可达 | 失败 | 失败 |
  | H_noise | 随机失败 | 不确定 | 可能成功 |

- **另加对称性检验**：从别处到达 r 之后，`go to r′`（r′ 是已知与 r 同址的容器）也应失败。
- **产出**：带证据计数的规律 L_co："`go to r` 无效 ⇒ 已在 r 的位置；同址是一个等价关系"。证据等级 [E]。
- **另一个产出（M1 的消融）**：从这些局的观察中统计"物体类型 → 容器类型"的出现频率，作为位置先验 P_loc。

### B 阶段：构造（只用 A 阶段的产物）

| 分支 | 内容 |
|---|---|
| G3-L | G2A-1 加上 L_co：`go to r` 无效时，按规律视为已在 r，用 `examine r` 取得 r 的状态并继续。其他字面监控保留，违反时弃权 |
| G3-S | G2A-1 改为只在每个达成器结束时检查后置条件（状态级监控，例如是否手持 T、是否已放入），忽略中间的字面不符；不用 L_co |
| G3-LS | 两者都用 |
| G3-LP | G3-L 加上位置先验 P_loc（按先验概率排列搜索顺序） |
| 对照 | G2A-1、B1 |

### C 阶段：评测（开发集中的新局）

训练集中按种子 68 抽 60 个新局，每类任务 10 个，与此前全部不重叠；每局 ≤ 50 步。B2 只在其中按种子 69 抽的 12 局上运行（同 G2 的协议与预算）。

### 预测（锁定）

| G3-a | A 阶段：区分实验全部支持 H_co，即每次 `examine r` 都成功、每次重试 `go to r` 都无效，矛盾数为 0；对称性检验也全部一致。B 采纳 L_co |
| G3-b | G3-L 的成功率 ≥ B1 − 0.03，且 ≥ G2A-1 + 0.10 |
| G3-c | G3-L 没有沉默失败：所有失败都是弃权；"自称完成却未成功"的局数为 0 |

### §G3-M2 实现细节（代码提交于任何正式运行之前）

代码：`experiments/g3/`（`g3_core.py`、`g3_discover.py`、`g3_run.py`、`g3_score.py`、`judge.py`、`games.py`、`g3_b2_subset.py`），以及 `experiments/b2/score_g3_b2.py`。以下几点是预注册没有写死、在写代码时定下的，在正式运行之前记录：

1. **对称性检验的操作化**：在局面 r0 上 `go to r` 失败后，记下 (r, r0)。下一次成功到达别处的容器 r″ 之后，发出 `go to r`。若到达，则计一次对称性检验，再发出 `go to r0`，H_co 预测"不到达"。若 `go to r` 在 r″ 也不到达，说明 r 与 r″ 也同址，不计检验（单列计数 `sym_back_colocated`）。
2. **矛盾数**：`examine` 失败数 + 重试到达数 + 对称性检验中 `go to r0` 到达的次数。G3-a 要求矛盾数为 0 且至少有一次对称性检验。
3. **区分实验本身的有效性**（在已用过的 G2-ALF 局上检查，不属于任何正式数据）：`examine r` 在 r 处成功 6/6；在开局（未到任何容器）时 0/36；到达另一个容器后对其他容器 0/42。即 `examine` 确实只在代理位于 r 时成功，能区分 H_co 与 H_un。
4. **位置先验 P_loc**：只从观察文本中点名了容器的列举句统计（"On the r, you see …"、"The r is open. In it, you see …"），按"物体类型 → 容器类型"计数。
5. **G3 的代理与 G2 的差别只在三处**：L_co（`go to r` 无效时 `examine r`，成功则在信念中记为到达 r）；`place` 只在反馈含"You move"时才把物体记为已放置；可选的状态级监控与先验排序。找灯的搜索与 G2 一样不打开容器（冒烟测试中发现 G3 初版会打开，已在正式运行前改回）。对照组 G2A-1 与 B1 直接用 G2 的 `alf_core.Agent`，不经过 G3 代码。
6. **沉默失败**：结局为"claims done"而裁判记录为未成功。
7. **G3-e 的步数**：主指标是 60 局全部的平均步数（与 G2 一致）；只在成功局上的平均步数作为辅助量报告。
8. **B2 子集**：评测 60 局中按种子 69 每类任务抽 2 局（与 G2 用种子 66 的分层方式相同），共 12 局，分 4 批，每批一个新的子 agent，提示词与 G2 逐字相同（只换套接字文件名）。
9. **冒烟模式** `--smoke`：只在 G2-ALF 已用过并已计分的 6 局上运行，输出写到 `$TMPDIR`，不进入任何结果。

### G4.5　跨域法则（H-XFER）：最小跨域反例（证明，先于 AppWorld 的持出测量写定）

**引理 X1（目标语言的表达边界）。** 设冻结核心的目标语言 L0 由原子的合取构成，原子的参数是常量，或是在回合开始时由首个观察绑定的变量（Mission 05 的 cue 绑定）。对一类环境，若存在两个初始状态 s、s′，首个观察相同，但某个查询 Q 的结果集不同（AppWorld：任务开始时代理只看到指令与主管信息，查询结果需要调用 API 才能得到），则：
1. 目标"对 Q 的每个结果 x 达成 W(x)"在 L0 中没有等价式；
2. 信息目标"提交的答案等于 f(Q 的结果)"在 L0 中也没有等价式。

**证明。** L0 中的目标是首个观察的函数：同一首个观察绑定出同一组原子，在 s 与 s′ 下指称同一个目标集合。但 1 与 2 的满足集合依赖 Q 的结果，而 Q 的结果在 s 与 s′ 下不同，所以存在一个状态在一种初始状态下满足目标、在另一种下不满足，而 L0 目标不能区分两者。∎

**前提与证据等级。** 证明本身是 [P]。"AppWorld 的首个观察不含查询结果"是环境协议的事实（任务开始时只给指令），[E]。P-AW-0 测得开发集的状态改变型任务全部依赖先前查询的结果（[E]，40 个任务）。因此在 AppWorld 上，冻结核心在任何适配器下都需要一次目标语言的扩展（运行中的绑定与迭代合同、信息目标），H-XFER 的"只换适配器"形式不成立。G4-k 只在持出集上测量信息目标的比例，作为反例类的流行度。

### G4b.2　开发依据（`experiments/g4b/g4b_scores_dev.json`；G3 评测局的房间，每族 10 个）

开发中的两处修正（都在裁判侧的生成器）：
- 第一版允许开局不在任何容器中的物体，以及官方任务从不使用的落地灯，产生了任何搜索者都找不到的目标；
- 50 步的上限使预算用尽占据了大多数失败。

修正后：

|---|---|---|---|---|---|---|---|
| CMP-0（冻结组合律） | 17/40 | 9/10 | 4/10 | 4/10 | **0/10** | 0 | 20 |
| CMP-1（升级合同） | 37/40 | 9/10 | 10/10 | 9/10 | 9/10 | 0 | 0 |

机制：冻结表按原子**种类**记录保持关系，并且没有手这一资源。在 F4 上，它要求两种处理都排在两个放置之前（"处理不保持放置"），于是第一次处理之后手里拿着物体 1，再去取物体 2 时 `take` 失败。冻结组合律在深度 4 上**认证了不可执行的顺序**。监控把它变成弃权，所以不是沉默失败。

- CMP-1 − CMP-0 = +0.45（区间 +0.333 到 +0.583，McNemar p < 10⁻⁷，27 : 0）。CMP-0 的 27 个失败全部是"take"处的监控弃权（手中已有物体），没有沉默失败。
- CMP-1 与 SEQ 逐局相同。
- 游戏原目标在任何回合中都没有被意外满足（三个分支与 B2 都是 0）。

**锁定判定：** G4b-a、b、c、d、e、g、h 成立；**G4b-f 不成立**（B2 的成功率 0.75 低于 CMP-1 的 1.00；步数 14.2 ≤ 0.8 × 26.4 一项成立）。

**按事先写定的解释：**
- G4b-a 与 G4b-b 成立：Mission 05 的组合律（按种类的两两保持）在外部环境的深度组合上**不健全**。它在 F4 上认证了 15/15 个不可执行的顺序。缺的是资源（手）上的适用性保持与按物体索引的保持。
- G4b-c 成立：补上这两类关系之后，合同推理与写入同样知识的经典方法逐局相同。
- G4b-f 不成立："构造器在复合目标上超过强 LLM 代理"。但见下面的 POST-HOC 诊断：B2 的全部失败集中在一个目标族上，原因需要先排除目标句的歧义。

**POST-HOC 诊断（计划写于运行之前；不改变判定）：** F3L 的目标句是"look at a T2 under the desklamp and put a T1 in/on the R"（两个子句的顺序随机）。锁定的判据要求回合结束时"拿着 T2、灯亮且在灯所在的位置"与"T1 在 R 中"同时成立。但"look at"在自然语言中可以读作一个瞬时事件：先看，再去放另一个物体。这样，B2 每个子目标都做到了，只是结束时不再同时成立。设计者不读 B2 的轨迹，所以用裁判侧的布尔记录检验：对同样 6 个 F3L 目标再运行一次 B2（新样本，2 批），服务器逐步记录"HOLDING+LIT 部分""IN 部分"与整个目标第一次成立的步数（只记布尔量与步数）。
- 若 HOLDING+LIT 与 IN 部分都曾成立，而整个目标从未同时成立：失败来自"事件 / 终态"的规格歧义，不是能力问题。B2 在 F3L 上的结果应视为规格不匹配，G4b-f 的反向结论不可靠。
- 若 HOLDING+LIT 部分从未成立：B2 在这类复合目标上确有能力缺陷。

**第一次 POST-HOC 诊断的结果（`experiments/g4b/posthoc_f3l.json`）：** B2 在 6 个 F3L 目标上重跑，全部失败；IN 部分在第 4–10 步成立，**HOLDING+LIT 部分在任何一步都没有成立**。所以失败不是"事件 / 终态"的歧义。另一个可能的解释是"就地查看，不拿起"：开局时要看的物体已经在台灯处的，24 个 B2 目标中的 6 个 F3L 里只有 2 个，不能解释全部。

**第二次 POST-HOC 诊断（计划写于运行之前）：** 再在同样 6 个目标上运行 B2，裁判侧逐步记录（只有布尔量与命令的第一个词）：是否拿着 T2、台灯是否开着、两者是否同时、两者同时且代理在灯所在的位置。区分：
- 若"拿着 T2 且灯开"出现过、但从未"在灯处"：裁判的位置条件与 B2 的做法不符（或 B2 在别处开灯），需要检查判据；
- 若"拿着 T2"与"灯开"从未同时出现：B2 的做法是不拿起物体，或在开灯之前放下了物体，这是对目标的另一种读法，或者能力缺陷。
