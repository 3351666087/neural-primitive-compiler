由静态扫描（AST）与动态访问日志确认：

1. 构造器路径上读取的真值**值**只有 `applicability_cex`，读者只有三个表构造函数：`a_dsl.a_tables`、`zplus.a_tables_plus`、`zpp.a_tables_pp`。它们另外读取 `preserves` 的键（由原子决定的模式列表，不含真值）。
   - 动态日志：三者只访问 `<instance> / applicability_cex` 与 `<instance> / preserves / <键>`。
2. `construct.py`、`cir_dsl.py`、`compile_cir.py` 与 B 的学习器都不读取任何真值字段。
   - 以 N ≤ 5 的真值建表后，把裁判的全部入口替换成抛异常的函数，再运行 A-P 与 A-P′：98 个目标中构造 59 个，**裁判调用 0 次**。
3. `truth.py` 没有标注所属侧，只导入构造器侧模块。所以"真值"是构造器自己的宏模型的有界穷举，与裁判的环境无关。Mission 05 中"0 个危险条目"一类的可靠性数字，衡量的是 Z3 编码与宏模型的一致性。
4. 裁判侧模块不导入任何构造器代码，与 Mission 05 的声明一致。但 `construct.py` 在模块层导入了裁判模块（`cir_interp`、`instances`），供其中的 `judge_plan` 使用。构造与判定在同一个模块、同一个进程里，分离靠约定，不靠进程或权限。上面第 2 条的动态测试表明，构造函数实际上没有调用裁判。
5. Mission 06 的新模块中，标为 CONSTRUCTOR SIDE 的（`app_r.py`、`concretize.py`）不导入真值或裁判模块（静态检查：0 处违规）。

## 3. 适用性：不读真值的参数化证明（G0-A1..A5）

**方法。** APP-R（`experiments/g0/app_r.py`）是对"合格状态中选择失败"的计数松弛：
- 位置类由区间交集给出：ZONE 的区、窗口 W1/W2 及其外侧、d 的左右与"距 d 不超过 k"；
- 每类按六种类型计数，并加入见证格；
- 窗口的极值性用必要条件编码；
- N 为符号整数。

UNSAT 即对一切 N ≥ 3 的证明，相对于编码与 Z3。三个范围：
- S_T：危险格 ≤ 2；
- S_D：再加物体 ≤ 7；
- S_A：危险格不限。

**结果**（AUD 共 217 个实例）：

| 集合 | 实例 | 真值适用（N ≤ 7） | APP-R 证明（S_T / S_D / S_A） | 真值有反例的实例：APP-R 状态 |
|---|---|---|---|---|
| LIB | 12 | 12 | 12 / 12 / 12 | — |
| G3-DEV | 15 | 8 | 8 / 8 / 8 | 7 个 NOT_PROVED |
| STRAT-DEV | 70 | 15 | 15 / 15 / 15 | 51 个 NOT_PROVED，4 个 UNKNOWN（超时） |
| G3-HO（POST-HOC 审计） | 48 | 35 | 35 / 35 / 35 | 13 个 NOT_PROVED |
| G4-HO（POST-HOC 审计） | 72 | 52 | 52 / 52 / 52 | 20 个 NOT_PROVED |
| **合计** | **217** | **122** | **122 / 122 / 122** | 91 个 NOT_PROVED，4 个 UNKNOWN，**0 个 PROVED** |

- **G0-A1 成立**：没有错误证明。另外，在 N = 8..12 上对 122 个实例各做 25,000 个合格随机状态的具体搜索（共 3,050,000 个状态），没有找到反例。
- **G0-A2 成立**：S_D 中的覆盖率为 122/122。
- **G0-A3 成立**：在 S_T 内没有找到 N > 7 的具体反例。
- **G0-A4 成立**：S_A \ S_T 中也没有。
- **G0-A5 成立**：12 个 LIB 实例在 S_A 中全部证明（非盲，见修正案 G0-1）。
- **复现**：重算的 N ≤ 7 真值与 Mission 05 五个存档的适用性（以及 G4 与第八轮的 good 标记）逐实例一致（0 处不同）。
- **成本**：真值 4,146 s CPU；APP-R 3,445 s CPU（实例 × 范围的中位数 0.18 s，p95 31.6 s，最大 143 s）。
- **真值反例首次出现的规模**：N = 3 有 67 个，4 有 11 个，5 有 7 个，6 有 10 个，7 有 0 个。

**解释。**
1. 在这五个集合中，Mission 05 每一条进度认证所依赖的适用性，都从"N ≤ 7 的宏模型穷举 [M]"升为"对一切 N、任意危险格数的参数化证明 [P]"。可信基是 APP-R 的手写编码与 Z3，Mission 05 的循环依赖由此去掉。
2. 但这一可信基并不小。APP-R 编码与 `dsl.select_dsl` 的一致性没有机器证明，与 Mission 05 的 Z3 损伤编码处境相同。支持它的是两项经验检查：
   - 1,402 个开发实例与 95 个有反例的 AUD 实例上，0 个错误证明；
   - 305 万个具体状态上，0 个反例。
3. 开发集表明，N ≤ 5 的适用性并不外推：8 个实例在 N = 6 或 7 首次出现反例，APP-R 都拒绝了，并由无界模型具体化出真实反例。N ≤ 7 对本语言（k ≤ 3）在所测实例上足够，但这是经验观察，不是截断定理。

## 4. 剥离 oracle 的构造（G0-C1、C2）

| 集合 / 路线 | A++（真值，Mission 05） | A++r（APP-R，不读真值） | A++0（无适用性证据）：构造 / 失败 / 比 A++ 少成功 / 新成功 |
|---|---|---|---|
| LIB A-P′ / A-P | 30 / 29，0 失败 | 30 / 29，0 失败，计划逐个相同 | 30 / 0 / 0 / 0；29 / 0 / 0 / 0 |
| G3-DEV A-P′ / A-P | 30 / 27，0 失败 | 同左，计划逐个相同 | 35 / **14** / 9 / 0；32 / **17** / 12 / 0 |
| STRAT-DEV A-P′ / A-P | 0 / 2，0 失败 | 同左 | 1 / **1** / 0 / 0；6 / **4** / 0 / 0 |
| G3-HO A-P′ / A-P | 30 / 29，0 失败 | 同左，计划逐个相同 | 35 / **5** / 0 / 0；35 / **10** / 4 / 0 |
| G4-HO A-P′ / A-P | 30 / 29，0 失败 | 同左，计划逐个相同 | 36 / **1** / 0 / 5；38 / **1** / 0 / 8 |

- **G0-C1 成立**：A++r 在每个集合、每条路线上构造的目标集合与计划都与 A++ 完全相同，0 失败。三个变体的 Z3 损伤、保持与度量条目逐项相同。在 ACH-DSL 上，A 的构造可以完全不读真值，额外成本是 APP-R 的证明时间。
- **G0-C2 成立**：去掉适用性证据后，构造出 **53 个在 J1-sym 或 J2 上失败的控制器**。并且由于构造器取第一个通过检查的候选，不适用的达成器会挤掉原来正确的计划：G3-DEV 上少成功 9 + 12 个，G3-HO 上少成功 4 个。适用性证据在 Mission 05 中是承重的。
- **附带观察。** G4-HO 上，A++0 多出 5 + 8 个在裁判下成功的目标。它们所用的达成器在单原子的合格状态中有反例，但在这些目标的闭环可达状态中没有遇到。适用性合同按"全部合格状态"表述，相对于具体目标是保守的。

## 5. 编译器（G0-K1、K2；定理见 `COMPILER_THEOREM.md`）

- **G0-K1 成立。**
  - 8 条神经元层引理（无记忆、截断、OR、AND、ATLEAST、常量、CMR 两条）都由 Z3 对符号扇入证明，前提非空。
  - Mission 05 的 G3/G4 全部路线、第八轮 A 路线与 G0-C1 的 304 个不同计划，在 N ∈ {5, 6, 7, 9, 12, 15} 上编译出的 1,824 个网络全部通过前提检查 P0–P5。
  - 检查器的负对照（阈值加一、删一个突触、D 太小、延迟为 2）都被检出。
- **G0-K2 成立。**
  - 类 C 中 10,000 个随机程序里，8,265 个属于 C_K。它们在 3,612,763 个比较步中，CIR 解释器与 NetBatch 0 处不一致；其中 822 个程序另与 npc 参考解释器比较，0 处不一致。C_K 内没有编译异常。
  - C \ C_K 的 1,735 个程序（寄存器从自身或更靠后的寄存器装载）全部被响亮拒绝。
  - 探索性变异：
    - ATLEAST k = 0：200/200 编译报错；
    - load 长度错误：70 个编译报错，130 个能编译，被前提检查全部标出，运行的 79 个没有不一致；
    - 节点 id 与输入通道同名：150 个编译报错，50 个能编译，被全部标出，运行的 50 个没有不一致；
    - REG_CONFLICT 之后网络与 CIR 分叉（111,279 步），这在定理范围之外（CIR 记为失败）。
- **结论。** 对类 C_K 中每个通过 P0–P5 的网络，编译正确性从 Mission 05 的抽样锁步 [E] 升为 [P]。可信基为 npc 语义、Z3、`compile_check.py` 与 T-K 的手证。
- **未覆盖：**
  - C \ C_K（编译器报错）；
  - 冲突之后的行为；
  - 运行协议之外的时钟。

## 7. 宏模型与环境的一致性（G0-M1）

- **方法。** 对 122 个真值适用的实例，比较两条序列：
  - 环境在"放下物体、手中为空"之后的格子序列；
  - 宏模型（`select_dsl` 加上逐次搬运）预测的序列。

  测试量为 N = 5 穷举（K ≤ 3）与 N = 9 随机 100 个，两种安全变体，共 1,681,260 个回合。
- **锁定判定：不成立。** 6 个实例上共 6,250 个回合被记为不一致。
- **POST-HOC 诊断**（`posthoc_fidelity.py`，不改变上述判定）：
  - 全部 6,250 个都是双方都在循环的回合：环境到步数上限 TIMEOUT，模型到 200 个宏步截断；
  - 环境序列与模型序列的同长前缀完全相同；
  - 真正的不一致（某个格子配置不同，或只有一方成功）为 **0**。
  - 这 6 个实例（S-GRO-0248、g3-grp-06、g3-grp-10、g3-zon-07 的右侧两个、g4-order-11）都是"适用但没有任何度量下降"的达成器，A++r 一个都没有认证。
  - 原比较要求完整序列相等，是测量工具的缺陷，在锁定前没有发现。
- **解释。** 在所测实例上，交换引理与选择编译和环境一致 [M]（N = 5）/ [E]（N = 9）。被认证的 99 个实例在真值中全部真正有进度。

## 8. 其余审计

- **G0-F1 成立**（`experiments/g0/claims_audit.md`）：没有把原子认证统计写成目标完成的句子。另外发现四处过度表述，类型与预测不同：
  - "对一切 N 的保证"；
  - 把 CIR 层的结果写成网络层的结果（两处）；

  - 实测部分：真值两次，各 4,146 s，其中一次因运行脚本崩溃而作废；APP-R 3,445 s。
  - 估计部分：并行阶段按"墙钟 × 8 个进程"估上界，约 4,000 s。
  - 超出的主要原因是崩溃后重算真值。没有单个实验触发 RESOURCE_LIMIT。开发运行另计，约 1 h，未计入。

## 9. 可信基（G0 之后）

| 环节 | 等级 | 可信基 / 界限 |
|---|---|---|
| 交换引理 | [P] 手证；在所测实例上与环境一致 [M/E] | G0-M1 |
| 损伤、保持、下降 | [P] | 手写的 Z3 编码；编码与宏模型一致 [M]（N ≤ 7） |
| 适用性 | [P]（122/122 个实例） | 手写的 APP-R 松弛编码 + Z3；经验检查见 §3 |
| 组合（L1，m ≤ 5） | [P] | Z3 |
| 资源检查 | 算术，覆盖 N ≤ 15、K ≤ 7 | `construct.py` |
| 规格 → CIR | 与宏模型一致 [M/E] | G0-M1 |
| CIR → 网络 | [P]，限类 C_K 与运行协议 | T-K 手证 + Z3 引理 + 逐网络前提检查 |
| 闭环成功 | [E]（J1-sym、S1、S2）、[M]（J2，N = 6） | — |

**仍然开放的缺口：**
1. 两份手写编码（Z3 损伤与 APP-R）与宏模型语义的一致性，只有经验支持，没有机器证明；
2. T-K 的归纳论证是手证；
3. "对一切 N 的控制器正确性"需要把上述各环节组合起来，目前没有端到端的机器检查；
4. 这一切只在设计者自己的 LINE / ACH-DSL 中成立，对外部环境没有任何含义（Gate 1 起处理）。
