# G4：第二次独立持出挑战——A++ 的校准（只准备，不运行）

写于第八轮之后。本文件、`G4_GENERATOR_BRIEF.md` 与 `G4_FREEZE.json` 一起提交，构成冻结。生成与运行都需要用户另行同意。

## 1. 为什么需要 G4

- **G3**：A 在 30 个独立达成器上可靠（Q1 成立），但只认证了 30 个真正有进度的实例中的 21 个（Q2 不成立）。
- **第七、八轮（DEV）**：A+ 与 A++ 把漏掉的推理接入了损伤与进度推导，在所有 DEV 集合上可靠、只收紧、不改变库。
- **未经检验的部分**：A++ 的校准。
  - G3-DEV 8/8；
  - 在用过的 G3 持出集上 30/30（事后，而 A++ 正是依据 G3 的失败设计的）；
  - 在均匀抽样的分层集合上 8/14（INCONCLUSIVE）。均匀抽样的语言中只有约 0.3 % 的程序真正有进度，不适合检验校准。
- 因此需要一组新的、由独立设计者写出的达成器：本会话没有见过它们，A++ 也不是依据它们设计的。

## 2. 持出的对象与范围

- 一个**新的独立会话**（全新上下文、新的空文件夹、不读取本仓库或任何其他生成任务的文件夹）用 ACH-DSL 写出 45 个达成器，每种原子类型至少 15 个，其中至少三分之二是它认为能达成的设计。
- 语言与 G3 完全相同（`G4_GENERATOR_BRIEF.md` 中的语言定义与 `G3_GENERATOR_BRIEF.md` 逐字相同）。只有数量与"至少三分之二"两处不同。
- 目标沿用 98 个 DEV 目标。

## 3. 冻结的内容

`G4_FREEZE.json` 记录以下文件的 SHA-256 与整体哈希；运行前用 `experiments/g4/freeze.py verify` 核对。
- 裁判与网络编译器（`experiments/judge/`、`src/cog/`）、库（`experiments/lib/`）。
- G3 的通用流程（`experiments/g3/*.py` 与库的规格）。
- A+（`experiments/r7/zplus.py`）与 A++（`experiments/r8/zpp.py`）。
- G4 的运行器、评分器与冻结工具（`experiments/g4/`）。
- 本文件与生成者说明。

## 4. 测量（`experiments/g4/run_g4.py`）

与 G3 的流程相同，只是 A 的表换成 **A++**：
1. 校验规格；
2. 计算 N = 3..7 的真值；
3. 计算 A++ 的表与可靠性，同时计算 A（G3 的编码）与 A+ 的认证，只用于比较；
4. 在 98 个目标上用 A++ 的表构造（A-P′ 与 A-P；只有持出达成器 / 库 + 持出达成器），经 J1-sym 与 J2 裁判；至多 10 个控制器做 J1-net 锁步检查；
5. B 与 G3 相同（只在 N = 5 上观察，n = 1000 与 200）；
6. 记录 B 文法分类。

评分：`experiments/g4/score_g4.py`。

## 5. 规程

1. 用户同意后，开启一个新的独立会话，把 `G4_GENERATOR_BRIEF.md` 原样交给它，工作文件夹为新的空文件夹。
2. 生成者只报告整体哈希与各类计数；本会话先提交这个哈希，再读取任何文件。
3. 用户同意后，把三个输出文件复制到 `mission-05/external/g4_heldout/`。核对哈希与 `G4_FREEZE.json`，然后运行 `run_g4.py` 与 `score_g4.py` 各一次。
4. 结果原样报告；之后的分析一律标注 POST-HOC。

## 6. 锁定的预测（与 `score_g4.py` 一致）

| 编号 | 预测 | 不成立时的含义 |
|---|---|---|
| P1 | **A++ 的可靠性**：(a) 由 A++ 的表构造的控制器在 J1-sym 与 J2 上 0 失败；(b) 没有 PROVED 的损伤上界低于 N ≤ 7 观察到的增量；(c) 没有带反例的 PROVED 保持条目；(d) 没有被真值否定的进度认证；(e) J1-net 0 处不一致、0 失败 | A++ 新加的约束或通用链条在独立输入上有错 |
| P2 | **A++ 的校准**：在 N ≤ 7 上真正有进度的实例中，A++ 认证 ≥ 90 %（这类实例少于 20 个时为 INCONCLUSIVE） | G3 之后的修正对新的独立设计不够 |
| P3 | **单调**：A（G3 编码）认证的 A+ 都认证，A+ 认证的 A++ 都认证 | 新约束在独立输入上削弱了已有的认证 |
| P4 | **残余缺口的形状**：A++ 未认证的每个真正有进度的实例，其规则都用到非 GROUP 原子上的窗口区域，或相对于 d 的来源区域（LEFT_OF_DEST、RIGHT_OF_DEST、within，可在 and 之内）（全部认证时为 INCONCLUSIVE） | 出现了第八轮没有见过的缺口类型 |
| P5 | **B**：由 B 的表（n = 1000 与 200）构造的控制器 0 失败；n = 1000 时，B 文法之内的规格的每个实例版本空间非空（≤ 64 对）、0 处不一致、没有低估的上界 | B 在第二个独立集合上不能复现 G3 的结果 |
| P6 | **成本**：整个运行 ≤ 2.5 小时墙钟；真值 ≤ 45 分钟 CPU | — |

**裁决**：
- P1 成立：A++ 的可靠性在第二个独立集合上得到确认。
- P2 成立：G3 暴露的校准缺口在独立设计上被闭合，这是 G4 的核心结论。
- P2 不成立而 P4 成立：残余缺口就是已知的形状（窗口或相对位置与区域的联系），下一步针对它。
- P4 不成立：记录新的缺口类型。
- 任何不成立都原样报告。

## 7. 有效性威胁

- **A++ 是看过 G3 的失败之后设计的**。G4 正是为此而设：它的达成器本会话没有见过。但生成者与 G3 的生成者、本会话属于同一个 LLM 家族，设计偏好可能相近，所以 G4 不是完全独立于 G3 的分布。
- **语言由本会话设计**，持出的只是语言中的程序。
- **适用性只有 N ≤ 7 的证据**；A-P 对任意 ORDER 达成器只能用度量最大值作步数上界。
- **说明要求至少三分之二是"能达成的设计"**，校准在偏向好设计的分布上测量。这正是需要的：校准关心的是真正有进度的实例。
- **独立性只能由说明约束**，无法强制。

## 8. DEV 干跑（`experiments/g4/dev_dryrun.json`；G3-DEV 的 8 个规格，已看过，不是持出）

- 15 个实例，8 个真正有进度。**A++ 认证 8/8**（A 7，A+ 7）。
- 没有低于真值的上界，没有错误的进度认证，构造 0 失败，10 个控制器 J1-net 0 处不一致。
- B 与 G3 干跑一致：文法之内 0 处不一致；文法之外 2 个实例漏掉移动，产生 2 个低估的上界，但没有进入任何证书。
- 评分：P1、P3、P5、P6 成立；P2、P4 为 INCONCLUSIVE（只有 8 个真正有进度的实例；没有未认证的实例）。
- 运行 1,040 s 墙钟，真值 367 s CPU。
